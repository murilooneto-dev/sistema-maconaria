# Fase 2 — Banco Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Criar as migrations, tabelas, constraints, índices, RLS e seeds para as 17 entidades restantes do modelo de dados do SPEC (§31), completando a Fase 2 ("Banco"). Nenhuma lógica de aplicação (services, Server Actions, UI) é construída nesta fase — só estrutura de banco, conforme SPEC §37 Fase 2 e CLAUDE.md §14.

**Architecture:** Migrations SQL puras em `supabase/migrations/`, numeradas sequencialmente após `00000000000001_profiles.sql`. Cada tabela financeira segue o padrão já estabelecido na Fase 1: `uuid` PK, `NUMERIC(12,2)` para dinheiro, `timestamptz` para carimbos de tempo, RLS habilitada com policy de leitura ampla para `authenticated` e policies de escrita restritas por role via funções helper (`is_admin()`, `is_tesoureiro()`), nenhum delete físico em tabelas financeiras (usar `status ATIVO/CANCELADO`).

**Tech Stack:** SQL puro (PostgreSQL/Supabase), sem dependências novas de aplicação.

## Global Constraints

- Nenhum delete físico de movimentação financeira — usar `status ATIVO/CANCELADO` com `motivo_cancelamento`, `cancelado_por`, `cancelado_em` (CLAUDE.md §8, SPEC §23).
- `NUMERIC(12,2)` para todo valor monetário (CLAUDE.md §6).
- Uma competência (`membro_id + ano + mes`) é única em `mensalidades` (SPEC §32, §7 do CLAUDE.md).
- `valor_devido = valor_grande_loja + valor_loja` em toda competência (SPEC §14) — constraint de banco, não confiar só na aplicação.
- Transferência não pode ter `conta_origem_id = conta_destino_id` (SPEC §32).
- RLS habilitada em toda tabela nova; nenhuma tabela "por enquanto" sem RLS (CLAUDE.md §11).
- Migrations imutáveis depois de criadas nesta sessão de trabalho — qualquer ajuste depois da task ser revisada e aprovada exige nova migration, nunca editar uma já commitada por uma task anterior deste plano.
- Cada migration deve rodar de forma limpa, na ordem, contra um banco vazio (silêncio de erros de dependência — FKs só podem referenciar tabelas já criadas em migrations anteriores).

## Decisões técnicas já tomadas (não bloqueantes, documentar em docs/banco.md na Task 13)

1. **Consistência agregada de pagamento** (soma de `pagamento_mensalidades.valor_aplicado` por competência não excede `valor_devido`) é responsabilidade da camada de domínio na Fase 6 (com testes Vitest), não de um trigger SQL — a Fase 2 é só estrutura.
2. **`fechamentos_mensais`** é um fechamento único agregado por `ano/mês` (não por conta) — `SPEC §29` já lista "Saldos por conta" como relatório separado.
3. **`repasses_grande_loja_itens.repasse_id`** é nulável — a criação automática do item ao quitar uma competência é lógica da Fase 9; a Fase 2 só cria a estrutura que suporta isso.
4. **RLS por role**: Administrador = acesso total. Tesoureiro escreve em `mensalidades`, `pagamentos`, `pagamento_mensalidades`, `movimentacoes`, `transferencias`, `campanhas`, `doacoes`, `recibos` (inserção apenas), `repasses_grande_loja(_itens)`, e pode **fechar** (não reabrir) `fechamentos_mensais`. Só Administrador escreve em `membros`, `contas`, `formas_pagamento`, `loja_config`, `config_mensalidade`, e só Administrador pode **reabrir** um fechamento (UPDATE em linha já `FECHADO`) — isso é imposto via RLS, não só na interface (SPEC §3, princípio 10).
5. **`recibos`** são imutáveis após criados (só INSERT, sem UPDATE/DELETE) — igual a `auditoria` e `config_mensalidade`.

```sql
create extension if not exists pgcrypto;

create or replace function public.current_profile_role()
returns text
language sql
stable
security definer
set search_path = ''
as $$
  select role from public.profiles where id = auth.uid() and ativo = true;
$$;

create or replace function public.is_admin()
returns boolean
language sql
stable
security definer
set search_path = ''
as $$
  select public.current_profile_role() = 'ADMINISTRADOR';
$$;

create or replace function public.is_tesoureiro()
returns boolean
language sql
stable
security definer
set search_path = ''
as $$
  select public.current_profile_role() in ('ADMINISTRADOR', 'TESOUREIRO');
$$;
```

- [ ] **Step 2: Criar `supabase/migrations/00000000000003_loja_config_mensalidade.sql`**

```sql
create table public.loja_config (
  id smallint primary key default 1 check (id = 1),
  nome text not null,
  logo_url text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

alter table public.loja_config enable row level security;

create policy "loja_config_select_authenticated"
  on public.loja_config for select to authenticated using (true);

create policy "loja_config_write_admin"
  on public.loja_config for all to authenticated
  using (public.is_admin()) with check (public.is_admin());

create trigger loja_config_set_updated_at
  before update on public.loja_config
  for each row execute function public.set_updated_at();

create table public.config_mensalidade (
  id uuid primary key default gen_random_uuid(),
  tipo text not null check (tipo in ('NORMAL', 'REMIDO')),
  valor_mensalidade numeric(12,2) not null check (valor_mensalidade >= 0),
  valor_grande_loja numeric(12,2) not null check (valor_grande_loja >= 0 and valor_grande_loja <= valor_mensalidade),
  valor_loja numeric(12,2) generated always as (valor_mensalidade - valor_grande_loja) stored,
  vigente_desde timestamptz not null default now(),
  criado_por uuid references public.profiles(id),
  created_at timestamptz not null default now()
);

create index config_mensalidade_tipo_vigente_idx on public.config_mensalidade (tipo, vigente_desde desc);

alter table public.config_mensalidade enable row level security;

create policy "config_mensalidade_select_authenticated"
  on public.config_mensalidade for select to authenticated using (true);

create policy "config_mensalidade_insert_admin"
  on public.config_mensalidade for insert to authenticated
  with check (public.is_admin());
```

Nota: `config_mensalidade` é somente-inserção (append-only) de propósito — o "valor atual" de cada `tipo` é a linha com o maior `vigente_desde`. Isso preserva histórico de configuração sem depender de snapshot só nas mensalidades. Nenhuma policy de UPDATE/DELETE é criada.

```sql
create policy "fechamentos_select_authenticated"
  on public.fechamentos_mensais for select to authenticated using (true);

create policy "fechamentos_insert_tesoureiro"
  on public.fechamentos_mensais for insert to authenticated
  with check (public.is_tesoureiro());

create policy "fechamentos_update_tesoureiro"
  on public.fechamentos_mensais for update to authenticated
  using (public.is_tesoureiro() and status = 'ABERTO')
  with check (public.is_tesoureiro());

create policy "fechamentos_update_admin"
  on public.fechamentos_mensais for update to authenticated
  using (public.is_admin())
  with check (public.is_admin());

create trigger fechamentos_mensais_set_updated_at
  before update on public.fechamentos_mensais
  for each row execute function public.set_updated_at();
```

Nota: a policy `fechamentos_update_tesoureiro` só permite UPDATE quando a linha **já está** `ABERTO` — ou seja, o Tesoureiro pode fechar um período aberto, mas não pode alterar uma linha que já está `FECHADO` (isso é reabertura, exclusiva do Administrador via `fechamentos_update_admin`). Essa é a regra "reabertura somente pelo Administrador" (SPEC §22) imposta em RLS, não só na interface.
